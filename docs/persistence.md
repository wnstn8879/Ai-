# 저장, 접근 권한과 마이그레이션

## 기존 데이터 보존

서버를 중지하고 SQLite DB 파일 또는 PostgreSQL 백업을 보관한 뒤 `backend`에서 `alembic upgrade head`를 실행합니다. 앱 import 시 자동 테이블 생성은 제거했습니다. 신규 설치도 먼저 마이그레이션해야 합니다.

- `001_legacy`: 기존 `rooms`, `messages`, `saves`가 있으면 그대로 채택하고 없는 테이블만 생성합니다.
- `002_identity`: 사용자, 세션, 멤버십, 개인 저장 ACL, 친구, 초대, 메시지 요청 영수증, AI 요청 횟수 테이블을 추가합니다.
- `003_message_order`: `(room_id, position)` 고유 인덱스를 추가합니다. 과거 중복 위치가 있으면 자동 삭제하거나 번호를 변경하지 않고 실패합니다. 해당 DB를 백업하고 명시적인 정리 계획을 세워야 합니다.
- `004_scene_snapshots`: `scene_states`와 `save_snapshots`를 추가합니다. 기존 방의 정적인 규칙과 캐릭터 이름을 상태 버전 0으로 보존하고 기존 체크포인트에도 연결합니다. 과거에 기록하지 않은 캐릭터 기억은 소급 추측하지 않습니다.

001·002·004 마이그레이션은 데이터를 지울 수 있는 downgrade를 차단합니다. 스키마 변경 전 백업으로 복원하는 절차를 사용하세요. 마이그레이션 파일의 스키마는 고정되어 있으며 실행 시 최신 ORM 모델에 의존하지 않습니다.

무인증 시절 방·저장 지점의 실제 소유자는 기록되어 있지 않습니다. 새 계정에 자동 배정하지 않으며, 계정으로 접근할 수 없어도 원본은 남습니다. 기존 데이터 복구가 필요하면 운영자가 소유권 증빙과 백업을 확인한 후 `room_members`에 소유자와 `save_owners`에 저장 소유자를 명시적으로 연결해야 합니다. 앱에는 누구나 방을 탈취할 수 있는 claim API가 없습니다.

## 방과 개인 저장

방 생성자는 owner, 초대 코드로 참여한 사용자는 participant입니다. 방의 모든 조회·메시지·AI·저장·분기 API에 멤버십을 검사합니다. 저장 지점은 **개인용**이며 다른 참가자에게 표시되지 않습니다. 소유자 본인이라도 방에서 나가면 기존 공용 방 저장 지점으로 접근할 수 없으며, 다시 초대받아 참여하면 자신의 저장 지점을 다시 조회할 수 있습니다.

메시지는 추가만 가능하며 현재 API에는 기존 메시지 삭제·수정이 없습니다. 저장 지점의 `message_index`는 포함할 메시지 개수입니다(0은 시작 장면). 복원과 분기는 새로운 solo 방을 만들고 메시지를 복사합니다. 원본·원본 참가자·원본 저장 기록은 변경하지 않습니다. 부모 ID와 분기 위치를 보존하므로 보관함에서 관계를 확인할 수 있습니다. 세계관·장면·캐릭터 상태는 메시지 개수 경계와 상태 버전으로 보존합니다. 체크포인트는 정확한 스냅샷 ID에 고정되므로 같은 메시지 위치에서 설정을 다시 편집해도 저장 당시 상태로 복원됩니다. 임의 메시지 분기는 그 위치까지의 최신 상태와 상태 변경 이력을 복사하므로 분기된 방에서도 더 과거 시점의 상태로 다시 분기할 수 있습니다.

## 동시성과 재연결

DB 방 행에 쓰기 잠금을 걸어 메시지 위치를 할당하고, 고유 인덱스로 충돌을 방지합니다. 클라이언트가 `request_id`를 보내면 같은 사용자의 같은 방에 동일 요청을 재전송해도 기존 결과를 반환합니다. 다른 본문이나 다른 메시지 API에 같은 ID를 재사용하면 409입니다. 모바일은 전송 실패 시 같은 내용의 재시도 ID를 유지하지만 앱 종료까지 보존하는 오프라인 전송 큐는 아직 없습니다.

AI는 트랜잭션 밖에서 호출하고, 저장 전에 최신 메시지 개수를 검사합니다. 생성 중 새 메시지 또는 상태 버전 변경이 있으면 409를 반환하고 사용자/AI 메시지 모두 저장하지 않습니다. 완료된 AI 턴 재시도는 기존 응답을 반환합니다. 동시에 들어온 미완료 동일 요청이 모델을 한 번만 호출하도록 보장하는 작업 큐는 아직 없습니다. 일일 요청 한도는 DB 잠금으로 사용자별·방별 시도 횟수를 제한합니다. 실패/충돌한 모델 시도도 한도에 포함하며 실제 토큰 비용 정산은 아닙니다.

WebSocket은 연결 직후 JSON 프레임 `{ "access_token": "..." }`으로 인증합니다. URL에 토큰을 넣지 않습니다. 메시지 전송은 HTTP API로 하고, WebSocket은 DB를 주기적으로 확인해 순서가 정해진 전체 스냅샷을 전달합니다. 프로세스별 메모리 브로드캐스트에 의존하지 않으므로 재시작·다중 워커에도 저장된 기록을 재전달합니다. 매 갱신에 세션 만료/폐기와 멤버십을 재검사합니다. 대규모 서비스에는 증분 이벤트·페이지네이션·브로커와 연결 수 제한이 추가로 필요합니다.

## 세션과 운영 경계

비밀번호는 scrypt(N=32768, r=8, p=3), 무작위 salt로 해싱합니다. 접근/갱신 토큰과 초대 코드는 SHA-256 해시만 DB에 보관합니다. 접근 토큰 15분, 갱신 토큰 30일이며 갱신 시 기존 세션을 원자적으로 폐기합니다. 로그아웃은 현재 세션을 폐기합니다. 모바일은 SecureStore에 세션을 저장하고 갱신을 단일 요청으로 합칩니다. 네트워크 오류는 세션을 지우지 않고, 만료된 갱신 토큰은 로그인 화면으로 돌아갑니다.

인증 요청에는 프로세스 단위 IP 제한(분당 30회)을 적용했습니다. 다중 워커에서는 공통 프록시/Redis 기반 제한이 필요하며 신뢰 프록시 설정과 함께 검증해야 합니다. 만료 세션·사용 완료 초대·요청 영수증의 운영 정리 정책도 추가해야 합니다. 서버와 DB는 운영 HTTPS/TLS·백업·비밀 관리 설정을 별도로 준비해야 합니다.

## 상태 API와 모바일 편집

`GET /rooms/{id}/state`는 상태/버전/경계 위치를, `GET /rooms/{id}/state/history?before_revision=N`은 이전 버전 최대 50개를 반환합니다. 읽기는 참가자에게 허용하고, `PUT /rooms/{id}/state`는 방장에게만 허용합니다. 쓰기 본문은 `{ "base_revision": 0, "state": { ... } }`입니다. 같은 버전을 두 사용자가 동시에 수정하면 하나만 성공하고 나머지는 409가 됩니다. 개인 분기의 생성자는 자기 분기에서 독립적으로 편집할 수 있습니다.

상태 필드는 세계관 규칙, 장소, 장면 요약, 중요한 사실, 캐릭터 목록입니다. 각 캐릭터에는 이름·성격·말투·목표·관계·현재 상태·중요 기억을 기록합니다. 이름 중복·항목 수·텍스트 길이·전체 UTF-8 크기를 검증합니다. 현재 단계에서 상태는 사용자가 명시적으로 편집하며 AI가 임의로 저장 상태를 변경하지 않습니다. 이 문맥을 LLM 프롬프트에 전달하지만 실제 모델의 기억 준수율과 응답 품질은 외부 호출로 검증하지 않았습니다.

모바일은 같은 방을 새로고침하거나 저장해도 작성 중인 대사와 실패한 전송 ID를 유지합니다. 상태 편집 중 다른 버전이 도착하면 초안을 덮어쓰지 않고 충돌을 표시합니다. 앱 종료까지 보존되는 초안 저장은 아직 없습니다. WebSocket 재연결은 단일 컨트롤러가 관리하고 백그라운드 복귀와 재시도 타이머가 겹쳐도 연결을 중복 생성하지 않습니다. 계정 전환 이후 도착한 HTTP 응답이나 이전 계정 갱신 결과는 세대 검사를 통해 폐기합니다.

## 공용 저장과 전원 동의 복원

005 마이그레이션은 기존 모든 저장의 `scope`를 `private`로 유지하며 공용 저장·참가자 세대·복원 제안/투표 기록을 추가합니다. 기존 개인 저장을 공용으로 공개하지 않습니다.

방장만 멀티플레이 방에 `scope: "shared"` 체크포인트를 생성할 수 있습니다. 공용 저장에는 이야기 상태 스냅샷과 저장 당시 사용자별 캐릭터 배정을 고정합니다. 방 참가자는 공용 저장을 읽거나 자기 개인 분기를 만들 수 있지만 다른 사람의 개인 저장은 계속 숨깁니다.

방장이 공용 체크포인트로 복원을 제안하면 현재 참가자 목록, 역할/배정, 메시지 개수, 상태 버전과 참가자 세대를 고정하고 15분의 동의 기한을 둡니다. 제안 생성은 방장 본인의 명시적 동의로 기록하며 앱에서 이를 안내합니다. 나머지 현재 참가자가 모두 동의해야 방장이 실행할 수 있습니다. 참여자는 실행 전 동의를 철회할 수 있고 거절/철회는 해당 제안을 종료합니다. 방장 취소와 만료도 실행을 막습니다.

투표 중 메시지 추가, 설정 편집, 참가자 출입 또는 캐릭터 재배정이 있으면 제안은 오래된 것으로 처리합니다. 같은 사용자가 나갔다 다시 들어오는 경우에도 참가자 세대가 달라져 과거 동의를 재사용할 수 없습니다. 방 읽기와 개인 저장은 제안을 무효화하지 않습니다. 새로운 공용 저장을 만들더라도 기존 제안은 원래 고정된 체크포인트를 계속 가리킵니다.

실행은 방 행 잠금 안에서 전원 동의와 원본의 변경 여부를 다시 검사한 뒤 **새 멀티플레이 방**을 만듭니다. 원래 방의 메시지·상태·저장은 삭제하거나 되감지 않습니다. 원래 방과 복원 방은 이후 독립적으로 진행합니다. 모든 현재 참가자와 역할을 복사하며 캐릭터는 체크포인트에 저장된 배정을 사용합니다. 저장 당시 없었던 현재 참가자는 미배정으로 시작합니다. 이미 나간 참가자를 자동 재참여시키지 않습니다. 참가자는 원래 방의 완료된 제안에서 복원 방을 열 수 있습니다.

동시/중복 실행은 같은 제안의 `result_room_id`를 반환해 방을 중복 생성하지 않습니다. 공용 저장·제안·투표 상태는 앱에서 5초 간격으로 확인하며 채팅 WebSocket과 분리되어 있습니다. 원본의 같은 방 ID 안에서 기록을 잘라내는 파괴적 롤백은 제공하지 않습니다.

공용 프로토콜의 주요 API:

- `POST /rooms/{room_id}/saves`: `{ "label": "선택 전", "scope": "shared" }` (방장)
- `GET /rooms/{room_id}/saves`: 본인 개인 저장과 해당 방 공용 저장만 조회
- `POST /rooms/{room_id}/restore-proposals`: `{ "save_id": "..." }` (방장)
- `GET /rooms/{room_id}/restore-proposals`: 최근 제안 최대 20개와 현재 유효성/투표 확인
- `POST /rooms/{room_id}/restore-proposals/{id}/vote`: `{ "accept": true }` 또는 `false` (본인 동의/거절/철회)
- `POST /rooms/{room_id}/restore-proposals/{id}/cancel`: 제안 취소 (방장)
- `POST /rooms/{room_id}/restore-proposals/{id}/apply`: 전원 동의와 최신성 재검사 후 결과 방 ID 반환 (방장)

새 제안이 유효한 동안 같은 방의 다른 제안을 만들면 409입니다. 만료되거나 진행 변경으로 오래된 제안은 새 제안을 만들 수 있습니다. 위 API에는 참가자 대신 투표하는 입력이 없으며 인증된 본인 ID만 사용합니다.
