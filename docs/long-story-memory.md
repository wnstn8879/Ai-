# 장편 기록 처리와 원문 기반 기억

## 이번에 해결한 문제

이전에는 모든 메시지를 DB에서 읽은 뒤 마지막 30개만 AI에 전달했습니다. 따라서 과거의 약속·사건은 최근 문맥에서 빠지고, 긴 기록과 보관함이 커질수록 API 응답도 커졌습니다.

현재 생성 경로는 전체 기록을 메모리에 올리는 대신 최근 30개 이하만 조회합니다. 과거 기록은 방별 역색인에서 관련 단어를 찾아 원문의 일부를 회수합니다. AI 입력에는 작가가 확정한 세계·인물 상태, 최근 기록, 관련 과거 구절, 이번 지시를 예산 안에서 넣습니다. 회수한 구절의 message ID·기록 순서·actor·Unicode 시작/끝 위치를 함께 보존합니다. AI가 만든 요약으로 원본을 덮어쓰지 않습니다.

## 온라인에서 확인하기

[기존 온라인 창작실](https://imagine-story-world.angksehdfur2468.chatgpt.site)의 작품을 열면 다음 기능을 사용할 수 있습니다.

- **지난 사건 찾기:** 인물·약속·사건의 단어를 입력하면 해당 작품의 원문 구절과 위치를 보여줍니다. 소설 본문과 작가 입력을 구분합니다. 찾은 소설 구절에서 개인 분기를 만들 수도 있습니다.
- **참고한 기록:** 이 기기에서 마지막으로 생성할 때 전달한 과거 구절과 최근 기록 수를 표시합니다. 생성 응답의 `context_report`는 요청 ID 영수증에도 저장되지만, 이 화면의 마지막 표시값은 계정·작품별 브라우저 저장소에 보관하므로 다른 기기로 자동 동기화되는 감사 보관함은 아닙니다.
- **이전 장면 더 읽기:** 기록을 30개씩 불러옵니다. 보관함은 작품 20개와 짧은 미리보기만 불러오고 ‘더 보기’로 이어갑니다. 처음에 읽는 모든 작품의 전체 본문을 받지 않습니다.

‘이어 쓰기’는 최신 진행에서 시작합니다. 과거 장면을 바꾸려면 구절 분기를 사용합니다. 화면에 일부 기록만 읽었더라도 저장 지점은 서버의 전체 메시지 수를 기준으로 만들며, 원본 기록이 화면 분량으로 잘리지 않습니다.

## 저장·인덱스·분기

`007_story_memory`는 `memory_cursors`, `memory_chunks`, `memory_terms`만 추가합니다. 원문·체크포인트·상태 이력을 수정하지 않습니다. 기존 DB는 백업 후 `alembic upgrade head`로 올립니다. 인덱스는 최초 사용 때 128개 메시지 단위로 정리하고 커서와 같은 트랜잭션으로 저장합니다. 한 번 정리한 과거를 매 생성마다 처음부터 다시 처리하지 않습니다.

색인은 Unicode NFKC/casefold 단어와 한글 두 글자 조각을 사용합니다. 원문은 변환하지 않고 Python Unicode codepoint 위치로 그대로 인용합니다. 긴 메시지는 480자, 60자 겹침으로 나눕니다. SQL의 `(room_id, term)` 인덱스에서 후보를 찾으므로 생성 때 모든 본문을 다시 훑지 않습니다. 외부 임베딩 서비스·API 키·추가 요약 모델 호출은 없습니다.

원본이 아닌 새 분기는 새 message ID를 사용하고, **그 분기에 실제로 복사된 본문만** 별도 색인합니다. 부모 방에서 분기 이후에 일어난 일이나, 구절 분기에서 잘라낸 뒷부분을 부모 인덱스로부터 가져오지 않습니다. 체크포인트 당시 확정 상태 복원과 기존 권한 검사를 그대로 사용합니다. 메시지 복사는 선택한 범위만 256개 단위로 처리하고 전체 분기 트랜잭션이 실패하면 함께 롤백됩니다.

## 모델 입력 한도와 정확성

`AI_CONTEXT_WINDOW_TOKENS`는 연결한 실제 모델/서버의 문맥 용량과 맞춰 설정합니다(기본 8192). Ollama의 `num_ctx`에도 같은 값을 전달합니다. 생성 출력과 템플릿 여유를 남기고 입력 텍스트의 UTF-8 바이트 수로 보수적인 예산을 계산합니다. 이것은 모델 전용 토크나이저로 측정한 청구 토큰 수가 아닙니다.

확정 설정·이번 지시·가장 최근 기록을 온전히 넣을 공간이 없으면 모델 호출/일일 요청 차감 전에 422를 반환합니다. 큰 설정을 몰래 삭제하거나 문장 일부를 잘라 완전한 사건처럼 전달하지 않습니다. 오래된 문맥은 일부만 회수하며 생략한 최근 기록 수와 실제 전달 구절을 보고합니다. 서버는 생성 도중 메시지나 상태가 바뀌면 기존처럼 오래된 결과 저장을 거부합니다.

프롬프트는 확정 상태 우선, 과거 구절의 시간·발언자 확인, 작가 지시와 확정 사건의 구분, 근거가 없으면 불확실하게 남기거나 질문하도록 요구합니다. **이 규칙이 모델의 모든 모순을 자동 검출하거나 기억 누락을 없애는 것은 아닙니다.** 검색은 단어 기반이므로 비유·동의어·이름 변경을 놓칠 수 있고, 긴 질의의 일부 검색어만 후보 검색에 사용합니다. 의미 검색·자동 사건 추출·모순 심사·작가 확인 흐름, 수십만 기록/다중 사용자 운영 부하는 다음 검증 범위입니다. 문맥 용량 환경변수만 늘린다고 모델과 하드웨어 용량이 늘지는 않습니다.

## 호환 API와 검증 범위

새 API는 인증된 `GET /library`, `GET /rooms/{id}/chapters?before_position=...`, `POST /rooms/{id}/memory/index`, `POST /rooms/{id}/memory/search`입니다. 기존 `/rooms` 전체 응답은 이전 모바일 호환을 위해 유지합니다. 웹은 새 페이지 API를 사용합니다. 모바일 발신 큐는 AI 호출 전 색인 정리를 완료하고, 정리 중 계정이 바뀌면 생성하지 않습니다.

이전 전체 응답을 받는 모바일 화면과 WebSocket 스냅샷까지 모두 대용량 페이지 방식으로 바뀐 것은 아닙니다. 공용 저장과 소유권 규칙은 유지하며, 무제한 데이터·모든 동시 접속 규모를 검증했다고 주장하지 않습니다. 온라인 AI와 원본 DB는 여전히 개발 환경에 있는 임시 연결입니다.

자동 검증은 SQLite 백엔드 77개, 모바일 39개, Worker 8개가 통과했습니다. 3,000개 기록에서 오래된 약속 검색과 제한된 AI 입력에 원문 포함, 중단/동시 색인의 중복 방지, 분기/체크포인트의 미래 사건 차단, 과도한 설정의 생성 차단과 차감 없음, 개인 데이터 접근 차단, 모든 페이지의 순서/누락 없음, 계정 변경 중 생성 중단을 확인했습니다. 자동 테스트에서 생성 모델은 대역이며 실제 모델 결과는 별도 기록합니다. PostgreSQL 재실행과 실제 휴대폰 브라우저 조작은 이번 환경에서 아직 확인하지 못했습니다.


## 실제 모델에서 확인한 문제

첫 실제 Qwen3 4B 실행은 3,000개 테스트 기록을 24개 배치, 2.65초에 색인하고 원문 약속을 회수했습니다. 입력 예산 7,180 안에서 5,270의 보수적 입력량을 사용했고, 생성은 125.64초에 성공했습니다. 하지만 **모델이 ‘열쇠를 동생에게만 맡긴다’는 약속을 ‘필요할 때만 연다’로 바꿔 회상**했습니다. 따라서 이 실행을 사실 일관성 통과로 기록하지 않습니다. [첫 결과와 평가](validation/long-memory-first.json)를 보존했습니다.

확인된 문제에 맞춰 회상 시 과거 약속/소유/생사를 변형하지 말고 과거 발언은 원문을 그대로 인용하라는 한국어 지침을 추가했습니다. 생성 후에는 ‘참고 기록과 비교’로 원문을 확인하도록 안내합니다. 이는 모델 출력의 정확성을 보장하거나 완전한 자동 모순 검사로 대체하지 않습니다.


동일한 3,000개 기록으로 지침 보강 후 새로 검증한 실행에서는 원문 약속을 그대로 인용했습니다. 색인은 24배치/2.81초, 모델 생성은 139.64초, 입력량은 5,557/7,180으로 확인했고 같은 요청 ID의 결과 재사용도 통과했습니다. [보강 후 결과](validation/long-memory-refined.json)를 참고하세요. 이는 한 가지 합성 테스트 사례에서의 개선이며 어색한 문장과 다른 사실의 검증, 일반적인 사실 일관성은 남아 있습니다.

최종 온라인 배포는 같은 주소에서 `succeeded`이며 Sites 소스 SHA는 `98e07bc38a531785da41dc7b0c8ff62ef267e91c`입니다. 앱 기능 커밋 `8aabd05`는 `feat/storyverse-auth-library-social`과 [PR #1](https://github.com/wnstn8879/Ai-/pull/1)에 반영합니다. main에는 병합하지 않습니다.
